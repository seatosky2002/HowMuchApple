# 데이터 품질 점검 기록 (2026-09)

운영 DB(74,758건)를 전수 감사하고 발견한 문제와 조치를 남긴다.
수치는 모두 운영 DB 또는 그 스냅샷 복제본에서 실측한 값이다.

관련 커밋: `21a3fde` `2a9509e` `23ae3a6` `267d7ee` `c5ddf13`

## 1. 해결한 것

### 1-1. 하루 주기 크롤이 12일간 전부 실패 (`23ae3a6`)

**증상** — 8/25 ~ 9/5, 크롤이 한 번도 성공하지 못했다. 스케줄러는 매일 정상
발화했고 3개 크롤러가 0.5초 안에 전부 실패했다. `crawler_log`에는 fail 행조차
남지 않아 **12일간 아무도 몰랐다.**

**원인** — `pool_recycle` 부재. MySQL `wait_timeout`이 8시간인데 크롤 주기는
24시간이라 풀의 커넥션은 배치가 돌 때 항상 만료 상태다. `pool_pre_ping`이 그걸
감지해 폐기하려는 순간 asyncmy가 이미 닫힌 uvloop 전송에 `ensure_closed()`를
호출해 `RuntimeError`로 터진다. 배치의 첫 DB 작업인 `CrawlerLog` insert가 여기서
죽었고, 세션 하나를 3개 크롤러가 공유해 첫 실패가 나머지를 연쇄 오염시켰다.

```
RuntimeError: unable to perform operation on <TCPTransport closed=True ...>
→ 크롤러 daangn 실패
→ 크롤러 bunjang 실패: This Session's transaction has been rolled back...
→ 크롤러 joongna 실패: (동일)
```

**조치**
- `pool_recycle=1800` — 만료 전에 버려서 죽은 커넥션 경로를 타지 않는다
- `run_all_crawlers` 실패 처리에 `rollback()` 추가 — 연쇄 실패 차단
- `_open_log()`로 첫 커밋 실패 시 롤백 후 1회 재시도 — 조용한 실패 방지

**검증** — 9/6, 9/7 양일 3개 플랫폼 전부 success.

**복구 불가한 손실** — `price_stats`는 "그날의 활성 매물"을 집계하는 구조라
8/25~9/4 버킷 11일이 영구히 비었다. 50일 중 39버킷만 존재한다.

### 1-2. 맥북에 존재하지 않는 사양 조합의 SKU 생성 (`21a3fde`)

**증상** — 애플이 판매한 적 없는 조합이 SKU로 등록돼 있었다. 30개 SKU, 매물 83건.

| 조합 | 매물 | 문제 |
|---|---|---|
| 맥북 프로 M3 + 18GB | 32 | 18GB는 M3 **Pro** 사양 |
| 맥북 프로 M5 + 48GB | 5 | base M5 최대 32GB |
| 맥북 프로 M4 + 16인치 | 3 | base M4는 14인치만 |
| 맥북 프로 M5 Pro + 16GB + 512GB | 2 | 램·SSD 둘 다 불가 |

**원인** — 제목의 숫자를 램으로 오인. `M5 Pro 16코어 GPU`의 16이 램 16GB로 읽혔다.

**조치** — `app/services/config_matrix.py`에 (모델, 칩셋)별 실판매 화면/램/SSD 집합을
고정하고, 벗어난 값은 파싱 오류로 보고 버린다. 검색 API(`resolve_sku`)도 같은
매트릭스로 막는다. 기존 유령 SKU는 `scripts/revalidate_macbook_skus.py`로 정리.

**검증** — 유령 SKU 30개 → **0개**. 매트릭스가 차단하는 매물은 96건(1.3%p)이고
내역이 M3+18GB(51) / M4+48GB(13) / M5 Pro+16GB(6) 등 **전부 판매자가 칩 티어를
잘못 쓴 매물**이라 차단이 정당함을 확인했다.

### 1-3. 제목 파서가 한 자리 GB를 못 잡음 (`21a3fde`)

**원인** — 공용 `_UNIT_GB_RE`가 `(\d{2,4})`라서 `8GB`를 한 건도 잡지 못했다.

**조치** — 맥북 전용 패턴으로 분리(`_MACBOOK_GB_RE`)하고, 단위 없는 조합 표기
(`16/256`, `(10코어, 16기가, 512)`, `14/48/1tb`)를 읽는다. 조합에 SSD로 해석되는
항이 없으면 버려서 `8/25`(날짜) 류 오탐을 막는다.

**검증** — 맥북 배정 45.2% → 55.6% (+780건), 회귀 0건. 신규 배정 64건 전수 검토.

### 1-4. 지역 매칭 모호 경고 하루 1,336건 (`2a9509e`)

**원인 두 가지**

1. **시드 중복** — 구가 설치된 시 13곳의 읍면동이 `부천시 중동`과
   `부천시 원미구 중동`으로 **둘 다** 존재해 후보가 2개가 되어 매칭을 포기했다.
   매물은 전부 구 없는 쪽에 붙어 있었다(부천시 중동 598건 vs 원미구 중동 0건).
2. **진짜 동명이동** — 역삼동(강남구 / 용인시 처인구), 다산동(남양주시 / 서울 중구).
   당근 주소는 동 이름뿐이라 가릴 수 없었다.

**조치**
- `app/db/dedupe_regions.py` — 44쌍 병합. 매물·시세 이력이 붙은 쪽을 정본으로
  남겨 `price_stats` 손실 0. 한 시의 서로 다른 두 구에 같은 동명이 실제로 있을 수
  있어, 구 없는 "시" 행이 섞인 그룹만 건드린다. 멱등.
- 시군구 접두 매칭(`_sgg_name_filter`) + 구체성 우선(`_narrowest_sgg_match`) —
  구를 생략한 주소도 계속 매칭되게
- 당근 앵커 185개의 (시도, 시군구)를 문서에서 생성해 tie-break 힌트로 전달

**검증** — 당근 지역 매칭 83.7% → 91.9%. 크롤 로그의 모호 경고 **0건**.

### 1-6. 지역 모르는 매물이 전국 시세에서도 빠짐 (`c5ddf13`)

**증상** — SKU는 확정됐는데 판매자가 지역을 안 적은 매물 6,986건이 시세 추이에서
통째로 빠졌다.

**원인** — `price_stats` PK가 `(sku_id, emd_id, bucket_ts)`인데
`snapshot_price_stats()`가 `emd_id IS NULL` 매물을 버렸다.
조회 쪽은 이미 전국 합산을 지원한다 — `get_price_trend`의 `emd_id=None` 분기가
emd를 무시하고 합산하고, `get_sku_with_price`는 `item`을 직접 집계해 애초에 지역
없는 매물을 포함한다. **즉 "현재 시세"는 맞았고 "가격 추이"만 틀렸다.**

**조치** — `emd_id=0`을 예약값으로 쓰고 emd FK를 제거(마이그레이션 `20260907_0002`).
가상 "미상" 지역 행을 만드는 대안은 `/api/v1/regions`가 지역 목록을 그대로 내려줘
UI 드롭다운에 노출되고 `region_matcher`·`dedupe_regions`에 새어들 위험이 있어
택하지 않았다.

**검증** — 스냅샷 복제본에서 15,517행 → 16,233행, 지역미상 206행에 매물 5,591건
편입. 전국 표본이 active 매물 수를 넘지 않아(2,335 vs 2,550, 차이는 IQR 이상치)
이중 계상 없음을 확인.

## 2. 플랫폼별 상태 판정 방법 (실측 캘리브레이션)

매물 54건 + 상세 페이지 9건을 직접 받아 대조한 결과. 다시 알아내기 어려운 정보라
남긴다.

| | 판매중 | 예약중 | 판매완료 | 삭제 |
|---|---|---|---|---|
| **중고나라** | 검색 `state=0` | 검색 `state=1` | **검색 `state=3`** | HTTP 404 |
| **번개** | 검색 `status=0`<br>= 상세 `saleStatus=SELLING` | 검색 `status=1`<br>= 상세 `saleStatus=RESERVED` | 상세 `saleStatus=SOLD_OUT`<br>(**검색엔 안 나옴**) | 상세 400<br>`ERR_DELETED_PRODUCT` |
| **당근** | JSON-LD `InStock` | `OutOfStock` + 배지 | `OutOfStock` + 배지 | HTTP 404 |

### 중고나라
- 검색 API의 `saleYn`을 `SALE_N` → `SALE_Y`로 바꾸면 판매완료 매물까지 나온다.
  "맥북 에어 M2 13인치" 실측: 43건 → 391건.
- **상세 페이지를 열 필요가 없다.** 검색 응답의 `state`로 판정 끝.
- 판매자 ID는 `storeSeq`. 같은 제목·가격 8건 그룹이 전부 동일 `storeSeq`였다.

### 번개
- 검색 `status=1`은 판매완료가 아니라 **예약중**이다(상세 API로 6/6 대조 확인).
- 판매완료는 검색에 안 나오므로 상세 재방문이 필요하다.
- 숨김 상품은 403 `ERR_NOT_HIDDEN_PRODUCT_OWNER`.
- 판매자 ID는 `uid`, 업자 플래그는 `bizseller`.

### 당근
- **상태 배지는 `<h1>` 제목 바로 앞의 `<span>`만 신뢰할 수 있다.** 페이지 하단
  "다른 매물" 카드에도 `거래완료`/`예약중` 문자열이 6~13회 나타나 단순 문자열
  검색은 오탐한다(class `f1uy1cm`/`f1uy1cn`).
- 클래스명(`_4y5lbr7` 등)은 빌드 해시라 배포마다 바뀐다 → 구조적 위치로 판정할 것.
- 짧은 URL `https://www.daangn.com/kr/buy-sell/{id}/`가 원본과 동일하게 동작하므로
  슬러그를 저장할 필요가 없다. 404는 슬러그 변경이 아니라 진짜 삭제다.
- 본문은 JSON-LD `description`에 전문이 들어있다.

### 성사 거래가 (중고나라 실측)
호가 대비 −14.3% ~ +4.5%로 **모델마다 다르다.** 일괄 할인율로 근사할 수 없다.
그리고 성사 표본이 호가 표본보다 많은 경우가 흔하다(맥북 에어 M2: 호가 31건 vs
성사 236건) — 호가는 현재 재고뿐인데 성사는 누적되기 때문이다.

주의: 여기서 얻는 값은 실제 거래금액이 아니라 **판매완료로 바뀌기 직전의 마지막
게시 가격**이다. 현장 네고는 반영되지 않으므로 실거래가의 상한으로 봐야 한다.

## 3. 미해결 (발견만 한 것)

### 3-1. 업자 대량 등록으로 표본 수 과장

같은 매물이 반복 등록돼 표본이 부풀려져 있다. 중복 그룹 1,796개 / 관련 매물
6,441건 / **초과 계상 4,645건**.

| 건수 | 가격 | 매물 |
|---|---|---|
| 122 | 5,600,000 | `[미개봉] 맥북프로16 M5 Max 18코어 CPU, 32코어 GPU 블랙...` |
| 105 | 5,200,000 | `미개봉 / 맥북프로14 M5 Max...` |
| 50 | 150,000 | `애플워치SE 40MM(A2351) 깨끗한 제품 판매합니다` |

평균가 왜곡은 작다(±1~3%). 문제는 **신뢰도 과장**이다 — `sku_id=206`은 표본
267건으로 표시되지만 고유 매물은 88건이다(3배).

판별 필드는 API에 이미 온다(중고나라 `storeSeq`, 번개 `uid`/`bizseller`).
저장만 하면 (SKU, 판매자, 가격) 중복을 접을 수 있다.

### 3-2. 표본 해상도 — `price_stats`의 75.8%가 표본 1건

최신 버킷 15,630행 중 1건 11,847행(75.8%), 2건 이하 90.3%, 10건 이상 0.9%.
원인은 지역축이 읍면동이라 287 SKU × 1,998 emd = 15,630조합으로 쪼개지는 것.

지역을 무시하면 327 SKU 중 129개가 표본 30건 이상이다.
**모델 단위로 올리면 47개 항목 전부가 표본 30건 이상**이 된다(표본 1건 0개).

모델은 `search_keyword`로 100% 확정되고 `item_attribute_value`에도 99% 저장돼
있어 추가 수집이 필요 없다. 모델 단위로 살아나는 활성 매물은 8,150건.

단 모델 하나에 용량이 섞이므로 범위로 표시해야 한다(iPhone 15 Pro 실측:
128GB 738,977원 ↔ 1TB 999,835원). 사양 미상 매물의 평균가(729,223원)가
128GB와 거의 같아 모델 평균에 넣어도 왜곡은 작다.

### 3-3. 판매/삭제 추적

| 소스 | sold 판정 | 비율 |
|---|---|---|
| daangn | 27,814 | 87.2% |
| bunjang | 61 | 0.4% |
| joongna | 3 | 0.0% |
| `deleted` | 0 | 세팅하는 코드가 0곳 |

판정 코드는 제목 정규식 하나뿐이고 플랫폼 분기가 없다. 당근만 되는 건 우연이다 —
검색 카드의 `거래완료` 배지가 `_parse_listing_text()`를 통해 제목에 섞여 들어온다.

`SOLD_RE`가 `예약중`까지 sold로 처리해 당근 961건이 시세에서 빠져 있다.
예약은 깨질 수 있어 `reserved`로 분리해야 한다.

### 3-4. 그 외

| 문제 | 근거 |

### 3-5. 제목 파싱의 상한

미배정 10,542건 중 **8,979건은 제목에 단서가 물리적으로 없다.**
iPhone은 3,247건 중 단서 있는 것이 9건, iPad는 2,391건 중 2건뿐이다.

미배정 맥북 34건의 상세 본문을 실제로 받아 재추출한 결과 **생존 32건 중 SKU 회복은
1건(3%)** 이었다. 본문 크롤링으로는 회복되지 않는다.

키워드/정규식 파싱의 실질 상한은 **85~86%**다.

LLM을 붙여도 표본 44건 직접 분류 기준 고유 기여는 9%였고, 대부분 SKU 추출이 아니라
노이즈 판별·모순 해소였다. 적용 여지가 있는 곳은 세 군데다.

1. 관용 표현 해석 — `기본형`, `풀칩`, `고급형`
2. 모순 해소 — 칩 티어와 사양이 안 맞는 96건
3. 노이즈 판별 — 액세서리 단품, 대여/렌탈, 빈 박스, "삽니다" 구매글

텍스트에 정보가 없는 68%를 채우려면 이미지(VLM)가 유일한 경로다.

## 4. 감사에 쓴 확인 항목

재발 점검 시 그대로 재사용할 수 있다.

- `item` 컬럼별 NULL/빈값, 가격·URL 이상치
- 고아 참조: `item`→`sku`/`emd`/`category`, `item_attribute_value`→`item`,
  `price_stats`→`sku`/`emd` (전부 0건)
- SKU 결함: 속성 없는 SKU, 매물 0건 SKU, fingerprint 중복/누락
- 중복: `(source, external_id)`, `url`, `(source, title, price)`
- 시세 집계 탈락: `status=active` 중 `sku_id`/`emd_id` 결손
- `price_stats` 신선도(최신 버킷)와 버킷 누락일
- `crawler_log`의 `running` 잔류 행, `fail` 이력
- 지역 NULL 분해: 주소 자체가 없는 것 vs 주소는 있는데 매칭 실패
