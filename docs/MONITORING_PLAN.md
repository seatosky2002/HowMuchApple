# 장애 알림 시스템 기획

> 코드 없음. 결정할 것을 정리하고 도입 순서를 제안하는 문서다.
> 판정 로직과 주기 점검은 PR #6에서 이미 만들었고, 이 문서는 **"어떻게 나에게
> 알림이 오게 하느냐"** 를 다룬다.

## 1. 왜 필요한가

8/25~9/5 **12일간 크롤이 한 번도 성공하지 못했는데 아무도 몰랐다.** 배치의 첫 DB
작업인 로그 insert 자체가 죽어서 `crawler_log`에 `fail` 행조차 남지 않았다.
사람이 직접 서버 로그를 보지 않으면 알 방법이 없었다.

그 사이 `price_stats` 버킷 11일이 영구히 비었다. 시세는 "그날의 활성 매물"을
집계하는 구조라 지나간 날짜를 되살릴 수 없다. **알림이 하루만 빨랐어도 손실이
1/11이었다.**

|---|---|---|---|

## 4. 감시는 2계층으로 둔다

한 계층만으로는 각각 사각지대가 있다.

### 계층 1 — 외부 감시 (GitHub Actions, PR #6에 구현됨)

밖에서 공개 엔드포인트를 찌른다. **서버가 완전히 죽어도 감지된다.**

- 장점: 서버와 독립. 시크릿 없이도 동작(현재)
- 한계: cron이 하루 1회라 **최대 24시간 지연**. 크롤이 07:40 UTC에 실패해도
  다음 09:00 UTC까지 모른다

### 계층 2 — 서버 내부 자기 점검 (미구현, 제안)

APScheduler에 점검 잡을 추가해 **크롤 종료 직후** 스스로 판정하고 알린다.

- 장점: **즉시 감지.** 12일 사고 때 백엔드는 살아 있었으므로 이 계층이 있었다면
  8/25 08:00 UTC에 알림이 왔다
- 한계: 백엔드가 죽으면 감시도 죽는다 → 계층 1이 그걸 잡는다

두 계층이 서로의 사각지대를 덮는다. **계층 2가 빠른 감지, 계층 1이 최후 방어.**

## 5. 알림 채널 — 선택이 필요하다

| 채널 | 설정 비용 | 금전 비용 | 도달 속도 | 필요한 것 | 평가 |
|---|---|---|---|---|---|
| **Discord Webhook** | 매우 낮음 | 무료 | 즉시(푸시) | Webhook URL 1개 | **권장.** 채널 만들고 URL 복사가 전부 |
| Slack Webhook | 낮음 | 무료(워크스페이스 있으면) | 즉시 | Webhook URL 1개 | Discord와 동급. 이미 Slack을 쓰면 이쪽 |
| GitHub 기본 알림 | **0** | 무료 | 수분~ | 없음 | cron 워크플로 실패 시 GitHub이 메일 발송. 공짜지만 수신자 제어가 안 되고 메일함에 묻힌다 |
| 이메일 (SMTP) | 중간 | 무료 | 수분 | Gmail 앱 비밀번호, `SMTP_USER`/`PASSWORD`/`FROM_EMAIL`, `ADMIN_EMAIL` | 기존 `send_email()` 재사용 가능. 스팸함 위험 |
| Telegram Bot | 낮음 | 무료 | 즉시 | 봇 토큰 + chat_id | 푸시 확실하지만 국내 사용률 낮음 |
| SMS | 높음 | **유료** (건당) | 즉시 | 국내 provider 계약(솔라피 등) | 심각 장애 한정으로만 |
| 카카오 알림톡 | 매우 높음 | 유료 | 즉시 | 비즈채널 + 템플릿 심사 | 현 단계에서 과하다 |

### 권장안

**1순위: Discord(또는 Slack) Webhook 하나로 시작한다.**

이유는 세 가지다.
1. 설정이 URL 하나라서 오늘 당장 붙는다
2. 무료이고 모바일 푸시가 즉시 온다
3. 계층 1·2가 **같은 Webhook을 공유**할 수 있어 구현이 단순하다

GitHub Issue는 그대로 둔다 — 푸시는 Webhook이 하고, **이슈는 장애 이력 보관용**으로
역할을 나눈다. 나중에 "지난달 몇 번 죽었나"를 볼 수 있다.

**2순위(나중): 심각 장애만 SMS.** `down`이 이틀 연속이면 SMS까지 올리는 식으로
심각도별 채널 분리. 유료라 지금은 보류.

## 6. 감시가 죽는 문제 (dead man's switch)

**가장 조용한 실패는 감시 자체가 안 도는 것이다.** 실제 위험이 이미 있다.

- `schedule` 트리거는 **기본 브랜치의 워크플로 파일만** 발동한다. 이 저장소의
  기본 브랜치는 `feat/backend-rebuild`인데 개발선은 `main`이다 → 그대로 머지하면
  **cron이 영구히 안 돌아간다**
- GitHub은 **60일간 저장소 활동이 없으면 cron을 자동 비활성화**한다
- 워크플로가 실패가 아니라 아예 실행되지 않으면 알림도 없다

그래서 "정상일 때도 신호를 보내고, 신호가 끊기면 그게 장애"라는 반전 감시가
필요하다.

**제안**: 무료 dead man's switch 서비스(healthchecks.io 등)에 매일 ping을 보내고,
ping이 안 오면 그쪽이 알려주게 한다. 설정은 URL 하나이고, **우리 감시가 죽는 것을
우리가 아닌 제3자가 감시**하게 되는 구조다.

이게 과하다고 판단되면 최소한 다음은 해야 한다.
- 기본 브랜치를 `main`으로 정리 (필수)
- 월 1회 워크플로 실행 이력을 사람이 확인

## 7. 알림 피로 방지

장애가 계속되는 동안 매일 같은 알림이 오면 결국 무시하게 된다.

| 규칙 | 내용 |
|---|---|
| 중복 억제 | 같은 장애가 이어지는 동안은 **처음 1회만** 푸시. 이후는 이슈 코멘트만 (PR #6이 이미 이 방식) |
| 회복 알림 | `ok`로 돌아오면 1회 푸시하고 이슈 종료 |
| 심각도 분리 | `down`은 즉시 푸시 / `warn`은 하루 1회 요약 |
| 조용한 시간 | 크롤이 06:00 UTC(15:00 KST)라 알림은 업무 시간대에 온다. 별도 처리 불필요 |

## 10. 범위에서 빼는 것

  알면 충분하다

  아니라 "배치가 안 돈다"다
- **온콜 로테이션**(PagerDuty): 1인 운영에 불필요
